# java-calculator

계산기 미션 저장소

### 구현 계획

#### 기능
1. 입력값에서 구분자를 판별 (기본 구분자 (,:) 인지 커스텀 구분자인지) 
   - 커스텀 구분자일 경우 헤더부분이 //로 시작함 
   - \n 뒤 부분까지 잘라서 전달해야함

2. 구분자를 기준으로 입력 문자열들을 구분하기

3. 구분된 토큰들의 숫자 여부, 음수인지 여부 판별

#### 테스트

- 일반적인 입력값에 대한 정상값 반환 
- 입력값이 Null 또는 공백이면 0 반환
- 정규식 특수문자가 들어가도 정상값 반환
- 요구사항에 명세된 것(숫자 이외의 값 또는 음수)이면 Runtime 예외 반환
- 커스텀 구분자 입력 형식이 올바르지 않으면 Runtime 예외 반환


### 고민한 점

#### 예외사항의 범위
- 문자열 계산기를 구현할 때, 예외사항의 범위를 어디까지 생각해야 하는지 궁금했습니다.
- 미션에 나와있는대로 [숫자 이외의 값 또는 음수를 전달하는 경우]만 생각해도 되는지, 
- 이외에는 예를 들어 Null 값 입력의 경우나, 잘못된 커스텀 구분자 입력 형식에 대한 것들이 있었습니다.

#### 입력값에 대한 가정을 세우기
- 이와 연관된 고민으로, Null 값 입력의 경우 이를 공백("")입력으로 생각할 수 있는지에 대해서 고민하였습니다.
- 일반적인 계산기의 경우, 아무것도 입력하지 않은 경우를 0으로 보고 있기에 이를 가정하고 구현하였습니다.
- 또한 구분자를 설정하는 과정에서 기본 구분자 [,:]와 커스텀 구분자를 혼용해서 사용하지 않는다고 가정하였습니다.


### Junit5만 사용했을 떄와 AssertJ를 사용했을 때의 차이점

- Junit5에서는 단순 동일 값 검증 이외에 추가로 여러 조건을 붙이게 되면 새로운 메소드를 계속 사용해야 해서 가독성이 떨어졌습니다.
- AssertJ는 검증 조건이 늘어나면 체이닝으로 계속 이어붙일 수 있어 한 줄에 검증 의도를 담기 쉽다고 생각했습니다.
- 예를 들어 예외를 검증할 때, 해당 예외가 어떤 타입인지와 그 메시지까지 같이 검증하는 경우 AssertJ를 사용하면 한 줄에 모든 조건을 다 검증할 수 있어 편했습니다.
- 또한 AssertJ의 isZero()등의 도메인 친화적인 표현을 통해 Junit5에 비해 의도를 더 쉽게 드러낼 수 있다고 생각했습니다.
